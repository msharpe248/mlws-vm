# MLWSVM Roadmap

Milestones M0–M52 are complete. What remains is the deferred performance
work (section 4). M0–M10 built the VM itself. The aim of
M11–M52 was to make MLWSVM worth targeting: programs on it should be able to do
real work (files, the OS, the network, text and data), and its distinctive
feature (isolated, parallel, supervised processes) should be easy to show off.
The scripting language is a separate project.

## Milestones M0–M10

| Milestone | Contents |
|---|---|
| **M0 Skeleton** | build, opcode table, encoding, disassembler |
| **M1 Assembler** | labels, expressions, directives, macros, includes |
| **M2 Loader and interpreter** | register windows, data stack, all addressing modes, verifier, test runner |
| **M3 Libraries** | imports and exports, library path, `lib/std` |
| **M4 GC heap** | strings, byte buffers, arrays, structs, lists, maps, handles |
| **M5 Structured exceptions** | |
| **M6 Processes** | many concurrent isolated processes: scheduler, messages, quotas, accounting |
| **M7 Tooling** | `mlwsvm top`, debugger, trace and profiler, web dashboard |
| **M8 Advanced types** | closures, BigInt, decimal |
| **M9 Performance** | quickening, cheaper frames, `_setjmp` (1.2–7.8× faster); the multi-threaded scheduler (work stealing; 8.2× on 16 CPU-bound processes). A generational GC and more specialised memory forms were measured and deferred (section 4) |
| **M10 Calling C** | extension API, declarative FFI, trusted installation (`mlwsvm ext`) |

| **M49 Cheaper frames** (done) | A function that never moves or reads SP or FP (no `push`, `pop`, `drop` or `enter`, no operand naming them) is stackless: its frames neither save nor restore the data-stack pointers, in the interpreter's pushes and pops and in the JIT's calls, returns and tail calls, since it leaves them as it found them; the frame records the flag. ## 1. Calling existing libraries (M10: done)

Done: the native-extension API (`include/mlwsvm/mlwsvm.h`), the declarative FFI
(`.extern`, via libffi), blocking and serial natives, foreign handles,
trusted installation (`mlwsvm ext`, SHA-256 pinning, permission checks), and
the foreign-call quota. See [EXTENDING.md](EXTENDING.md).

Variadic functions (1.1), C structs (1.2) and finalizers for `.extern`
handles were added in M17, callbacks (1.3, 1.4) in M18, and the binding
generator in M20, and the Windows trust check (1.5) in M47.

### 1.1 Variadic functions (M17: done)

`...` in an `.extern` parameter list ends the fixed parameters, and the call
goes through `ffi_prep_cif_var`. That matters on Apple arm64, where variadic
arguments go on the stack even when registers are free. Each declaration fixes
the variadic part's types, and C's promotions are enforced: `f32` and integers
narrower than `int` are refused after `...`. Format strings remain trusted
input: a wrong `%s` or a `%n` crashes or corrupts memory as it would in C.
`text.format` is the safe way for MLWSVM code to format text.

### 1.2 Structs by value and by pointer (M17: done)

`.cstruct NAME` … `.ends` declares a C layout and a struct of the same name;
`.extern` passes it as `struct NAME` (by value, and as a result),
`struct* NAME` (a pointer to a copy, copied back after the call) or
`out struct NAME`. Fields are numbers, `cstr`, `ptr<tag>`, nested structs and
fixed arrays of numbers (`u8[N]` as a byte buffer, others as a list). A struct
crosses the boundary as a copy, so pointers into VM memory never escape. The
VM computes C's offsets itself and checks them against libffi's size.

Not supported: bitfields, `#pragma pack` and unions (declare a union as a
`u8[N]` of its size). Layouts that differ by platform (`struct stat`) are best
generated from the system headers (see 1.5).

### 1.3 Callbacks during a call (M18: done)

`.callback NAME (params) -> (result)` declares a C function-pointer type, and
an `.extern` parameter `callback NAME` takes a closure, which becomes a libffi
closure for the duration of the call. The interpreter is re-entrant: the
callback runs in the calling process, on top of the frames of the foreign call,
until it returns. An uncaught exception stops at the callback and is raised when
the foreign call returns, so it never unwinds C. A callback cannot wait
(`E_CALLBACK`). The call's arguments are pinned against the collector while it
runs. Callbacks may nest, and work in blocking calls (on the I/O thread).

### 1.4 Asynchronous callbacks and posting messages (M18: done)

`.callback NAME (params), async` makes callbacks that C may call later, from any
thread: `ffi.async_callback(type, pid)` makes a function pointer whose every
call becomes a `Callback{name, args}` message. Extensions post messages from
their own threads with `api->post_int` and `api->post_str` (Erlang's
`enif_send`), and `api->hold` tells deadlock detection that messages may still
come. A callback that must return a value to C from another thread is not
supported. It would have to block that thread until the process replied.

### 1.5 Other

* **A binding generator** (M20: done): `mlwsvm bindgen header.h` writes
  `.extern`, `.cstruct`, `.callback` and `.const` declarations from clang's
  JSON syntax tree ([TOOLING.md](TOOLING.md#bindings-generator-mlwsvm-bindgen)).
  Run on the target machine, it also solves platform-dependent layouts.
* **Finalizers for `.extern` handles** (M17: done): `.ffi_free db,
  "libsqlite3", "sqlite3_close"` frees every `ptr<db>` when it is collected or
  released with `foreign.release`.
* **Windows** (M47: done): `plat_path_trusted` checks the owner and the
  access control list, as POSIX's checks the owner and the permission bits.
* ~~Hot code reloading~~ (M55: done).

## 2. Standard library (M12–M15 and M19: done)

M19 added `time` (clocks, ISO 8601, calendar dates), `hash` (CRC-32, SHA-256,
SipHash), `random`, the encodings (hex, base64, URL, CSV), `list.sort` and
`list.bsearch` with closures, set operations on maps, and integer maths; see
[STDLIB.md](STDLIB.md). The table below was the plan.

Proposed scope: everything that needs the operating system, or must be fast and
correct (parsing, formatting, hashing), lives in the VM's standard library. Pure
algorithms and idioms belong to the scripting language's own library, built on
top. Details are in the design discussion; this list is the starting point.

| Module | Contents |
|---|---|
| `std.io` / `std.fs` | files (open/read/write/seek/close), stdin/stdout/stderr, directories, paths, file metadata |
| `std.os` | command-line arguments, environment, exit, running external commands (with pipes) |
| `std.net` | TCP and UDP sockets, DNS; non-blocking underneath, so only the calling *process* waits |
| `std.time` | wall and monotonic clocks, ISO 8601 formatting and parsing, durations |
| `std.text` | printf-style `format` (number parsing exists: the `parse` instruction), UTF-8 iteration, validation and case mapping, split/join/trim/find/replace |
| `std.encoding` | hex, base64, URL encoding, JSON parse and serialize, CSV |
| `std.hash` / `std.random` | SipHash, CRC-32, SHA-256; a seeded PRNG plus OS entropy |
| `std.collections` | sort and binary search (with a comparator closure), set operations on maps |
| `std.proc` | a process registry (name → pid), request/reply calls with timeouts, supervisors, worker pools |
| `std.math` | (exists) plus integer helpers: gcd, powmod, bit operations |

Later, through the FFI rather than written from scratch: compression (zlib),
SQLite.

Capabilities: M60.

## 3. Platform

* Linux and CI: M11.
* Windows: M47, on x86-64 with Clang (MSYS2); arm64 too, with the JIT,
  tested in the Platforms workflow; sockets waited for on an I/O completion
  port (M71), and children's output as overlapped pipes on the same port
  (M86). Not done: MSVC builds, and waiting without looking every
  millisecond for anonymous pipes (a child's stdin, a stdin given to the
  VM), which have no readiness to wait for, and for pipes waited for writing.

Not done in hot reloading (M55, M72, M76, M94): moving a
process's own state for one that is not a `std.server` is the program's, with
`module.watch` and `module.current`, as in Erlang it is `sys`'s and the
program's own.

Not done in single executables (M54): signing on macOS. `codesign` signs the
executable but rejects the program appended to it, so a bundle cannot be
notarized. Doing it means writing the program inside the Mach-O file (a
segment of its own before `__LINKEDIT`, and every load command's offsets
moved), which waits until bundles are to be given to other people's Macs.

## 4. Performance (when measurements call for it)

Each of these was measured and deferred; see [PERFORMANCE.md](PERFORMANCE.md).

* ~~A size-class allocator for the GC heap~~ (M21: done).
* ~~Threaded dispatch, cheaper calls, compact operands for the quickened
  forms, field and element shapes~~ (M22: done).
* ~~The shapes compiled Lox emits~~ (M24: done). ~~Compiled Lua's~~ (M29: done). More specialised shapes
  (arithmetic directly on elements, raw memory), when compiled programs show
  them in the profiler's list of general-path instructions.
* A compact decoded form for every instruction. Quickened instructions carry a
  compact copy since M22 (an `Insn` is 32 bytes), but each decoded operand
  still takes 72 bytes. Measured after 0.19.0 on fifteen of the compilers'
  benchmarks (Erlang, Lox and Lua): the operands are all but never read, since
  every instruction but a few of `ring`'s sends and receives runs a quickened
  form; the hot instructions take 2 to 100 KiB of `Insn`s (`--trace`, the
  largest with their start-up code), within L2 everywhere and mostly within
  L1. Doubling `Insn` to 64 bytes cost nothing beyond noise on the M5, with or
  without the JIT; on the i7 and the Ryzen, with the JIT off, Erlang's `nbody`
  (58 KiB hot) 5.9% and 4.6% and the rest within 3%, and with it within 3%. So
  halving it would gain at most a few percent on the largest interpreted
  programs, and nothing with the JIT: not worth a second decoded form.
* ~~Calls: one window per frame~~ (M28: done). Calls without copying, through
  overlapping windows, would need an ABI change; only if call-heavy programs
  show the argument copies.
* ~~A generational collector~~ (M44: done). The one built in M31 saved too
  little while the interpreter was the cost; with the JIT, re-marking what
  programs keep was most of the collector's time. A remembered object is
  rescanned whole; card marking would make large containers written now and
  then cheaper still.
* ~~Clearing only the registers a function may read before writing them, and
  its `R` bank~~ (M33: done).
* ~~Bump allocation~~ (M46: done). Without moving objects, a line stays in
  use while any object on it lives; Immix's evacuation of fragmented chunks
  would need every pointer C holds across a callback to be pinned, and is
  only worth it if programs show memory held that way.
* Lock-free run queues and spinning before sleeping, for many-thread,
  message-heavy programs (M35 wakes idle threads one at a time instead).
* ~~Workers that poll~~ (M97: done).
* Selective receive in the VM. Measured after M97, on compiled Erlang's
  `ring` (1,000 processes passing a message a million times, 205 ns a hop on
  the M5; BEAM 170), against hand-written rings of the same shape: plain
  `send` and `recv` of an integer take 65 ns a hop; wrapping each message as
  the `[R, I]` list a compiled Erlang term is sent as, 147; receiving through
  a function that first looks at a list of messages saved by earlier
  receives, as compiled Erlang's `receive` does, 164. So the saved list costs
  about 8%, and a VM primitive to take the first message that matches could
  save no more: not worth an instruction. The wrapper costs 40%, and needs
  nothing new: sending a term as the one value it is (its `I` when `R` is
  null, else its `R`) and receiving into a list element, which keeps its type
  tag, read by `tagof`, takes 96 ns a hop. Compiled Erlang now sends and
  receives that way: its `ring` takes 110 ns a hop with the JIT, against
  BEAM's 170 (the JIT compiles `tagof`, and `recv` into an element costs what
  into a register does, so no new forms were needed).
* ~~A bytecode optimizer~~ (M41: done; [OPTIMIZER.md](OPTIMIZER.md)).
  Removing type checks needs the source language's types, so that stays in
  the compilers.
* ~~A JIT~~ (M43, M44: done; [JIT.md](JIT.md)). It keeps registers in machine
  registers within a block or a loop (across up to two calls in a loop on
  arm64), and compiles a closure call for the function it called last (M48),
  but does not speculate on types otherwise or inline. On x86-64 it
  keeps 5 integer registers. Measured after M48 on the i7 and the Ryzen: 4
  are as fast as 5 on every program, and a sixth (the slice's count moved
  into memory to free r13) made most programs 3–40% slower, since every
  block's count then goes through memory. So x86-64 gaining less from the
  JIT than arm64 is not the register count. Counted with Valgrind's
  callgrind after M51, the x86-64 code is about as long as arm64's for the
  same instructions; the i7 runs it at about half the M5's instructions a
  cycle. What is left is the processors' difference.
* Type speculation in the JIT, and keeping registers across the places where
  slow paths rejoin. Measured after 0.15.0, on compiled Lua's `nbody` and
  `methods`, Lox's `trees` and `zoo`, and Erlang's `nbody` and
  `binarytrees`, with each instruction's count and, on x86-64, callgrind's
  count of each machine instruction:
  * **Checks.** Checks of R registers (null, a constant tag, a type) are
    8–31% of the machine code's instructions, and none is redundant as the
    code stands, since slow paths rejoin and may change a value's tag.
    Treating code that never ran as a side exit would make 1–8% of the
    machine instructions redundant checks, and 0–6% checks a loop could
    hoist.
  * **Merges.** 57–98% of the labels run have only one predecessor that ran,
    but keeping registers across them would save 0.1–1.1% in loads and at
    most 0.8–4.4% in stores.
  
  What the machine code spends is spread over checks, branches and memory,
  with no one overhead left to remove, so neither is worth its complexity.
* Inlining in the JIT. Measured in M48: of the calls in the compilers'
  benchmarks, few go to small functions that call nothing (none in `fib`,
  `binarytrees` or Lox's `trees`; 22–29% in Erlang's `nbody` and `sorting`),
  and an inlined function needs its frame made at every way out of its code
  (a side exit, the slice's end, a trap), since the collector and the
  unwinder find registers through frames. Making every call cheaper reached
  recursive calls too (M49). What inlining could still gain, measured with
  the optimizer's own inliner (`--opt 3` against `--opt 3,-inline`, with the
  JIT, on the M5): Erlang's `sorting` 1%, `nbody` 2%, `binarytrees` 2%
  slower, Lua's `nbody` nothing; only compiled Lox's `invocation`, which is
  nothing but calls, 8%. Not worth frames built at every way out of an
  inlined body.
* Faster refills of the allocator. Measured after M48: reading a chunk's
  line marks 8 at a time gained nothing, and skipping holes of fewer than 2,
  4 or 8 lines (new chunks instead) gained at most 3% on compiled Lox's
  `instantiation`, whose survivors leave holes of 1–7 lines, for up to 75%
  more chunk memory; other programs were unchanged. The allocator's slow
  path is mostly zeroing the memory it hands out.
* ~~Compiling the string builders~~ (M51: done). `strcat`, `bufcat`,
  `tostr`, `substr`, `bufnew` and `bufpush` have quickened forms, which the
  JIT calls.
* ~~A generic string replace~~ (M51: done; `text.replace_n`, for the Lua
  compiler's `gsub` of a plain pattern).
